## 1. Objective / boundaries
Create one extensible AstrBot plugin, proposed id `astrbot_plugin_third_party_platforms`, plugin-list name `冷月系—第三方平台`, sidebar `（月）第三方平台`; author YepStar, same Cold Moon family. Initial built-in providers: Bilibili + Xiaoheihe, extracted from the LOCALLY INSTALLED, customized market plugins, not fresh upstream copies. Users configure their own bot accounts/login tokens. Bot can autonomously browse, evaluate, comment/reply, and share interesting content with its configured owner. Preserve platform-specific capabilities, elevate reusable policy/services to host level. Support subsequent providers without modifying scheduler/evaluator/storage internals.

User-required integrations: optional shared memory through 并行记忆分支; optional 网易云音乐 integration with host planning taking over autonomous listening; 自然意图分析 can read/create/change schedules using natural language. Do not merge these independent Cold Moon plugins into this repo. Do not recreate removed B站经历手帐/Gemini diagnostics. Do not silently replace persona, private companion, global model-cost guard, book/music/intent functionality already supplied elsewhere.

Repository publication and live cutover follow successful development/migration validation; the user authorized eventual replacement and uninstall of both legacy plugins after success. Initial two adapters are bundled implementations, not runtime wrappers requiring the two old plugins to remain enabled. Music remains a separately installed optional integration.

## 3. Required architecture
Host owns: provider registry/capability negotiation, account/profile lifecycle, login-state presentation, durable 24h planning/execution, evaluation/taste learning, share selection/delivery, permissions/isolation, reservations/rate limits, logs/retention, action receipts and memory gateway, authenticated UI, tool facade.
Provider owns: API/auth/signing/pagination/content acquisition/rendering, identifiers, supported write methods and limits, notification parsing/event transport, platform-specific configuration and semantics. No copied standalone Star registrations, duplicate background loops, or shared module-global account state.

Proposed provider API v1 (versioned contract; async where I/O): manifest/capabilities/config schema; account_status/login/refresh/logout; discover/query/read_content; poll_notifications/normalize_event; execute(action, context, idempotency_key); lookup_receipt where supported; initialize/close. Unknown capability => explicit unavailable, not a fake successful fallback. New providers register through one documented mechanism; settings panes generated/extended from schemas.
Normalized identity/content/action models must include provider_id, account_id, canonical external id, source URL, actual actor identity, source trust/scope, timestamps/timezone, provenance/evidence and available modalities. No fabricated text/video/audio consumption: subtitle-only reading is labeled as such. Stable key namespace prevents collisions across platforms/accounts.
Action receipt: planned/claimed/executing/succeeded/failed/unknown/cancelled/skipped; destination and externally confirmed ids. LLM suggestion is NEVER execution receipt. Claim before external side effect. Unknown delivery does not automatically retry, including after restart. Prefer reconciliation where API supports it. Reserve/release/settle budgets atomically, define crash recovery; no exactly-once claim where upstream cannot guarantee it.

## 4. Shared evaluation / sharing / learning
One host evaluation contract with normalized 1–10 score, rationale, evidence, interests/preferences, novelty, optional draft comment, recommendation intent; per-platform evidence differences remain visible. Configurable shared rubric and minimum owner-share score apply to EVERY provider (including music when opted in and meaningful). Threshold is necessary, not sufficient: permissions, provenance, explicit share-enabled state, daily/global quotas, recipient route, dedupe/cooldown and actual suitability also gate delivery. Unsupported/inadequate evidence => skip evaluation-dependent writes, not fabricated high score. Missing/invalid evaluation cannot pass threshold.
Separate thresholds/toggles for comment, like, follow, etc.; high score must not authorize unrelated writes. Preserve Bili per-action score thresholds as override options under shared defaults. Global policies are enforceable bounds; provider overrides cannot silently weaken a global minimum/cap.
Learn bot content tastes and time-of-day platform preferences from grounded observations and explicit owner feedback. Distinguish bot's own taste from owner's taste and third-party statements. Store evidence/count/confidence, timestamps, decay, exploration settings and version; persists across restart, can inspect/reset/disable. Sparse evidence must not turn a preference into a certainty. Learn from actual browsing/feedback, not self-authored plan assignments or unexecuted suggestions. No private user facts mined from external posts.
Owner sharing supports selected configured private channel(s), actual title/link and natural persona expression, not fixed robotic notification text. Review attribution across all providers; never turn a poster's “I” into owner “you”. Separate public response policy from private owner-share policy. Global and per-channel dedupe prevent two adapters sharing the same item twice.

## 5. Unified 24h autonomous planning
One planning authority across Bili/XHH + opt-in music + future providers. Configurable timezone (default Asia/Shanghai), allowed activity/sleep windows, activity level, global/provider action ceilings, browsing rounds vs content count vs write count separately. “24h” means full-day planning coverage, NOT mandatory continuous activity. Zero activity is valid; no quota-filling. Calendar windows may overlap, cross midnight and recur; do not inherit XHH fixed 08–23 or no-midnight constraints.
Generate bounded daily plans from persona, explicit constraints, eligible providers/account readiness, learned temporal/platform preferences and current actual state. Configurable generation time/after-sleep behavior and bounded retries; cached plan with config/learning fingerprint. Time-slot preferences emerge and persist over days, with exploration; user fixed/pinned windows always win. Manual rescheduling must survive automatic regeneration.
Persist Plan(id/date/timezone/revision), Task(id/provider/account/action/window/start/duration/status/origin/pinned/dependencies), reservations/execution history, explanations. Support list/detail/create/edit/move/cancel, preview/regenerate, pause all/provider. Editing uses revision checks; no resurrected cancelled/past tasks. Describe conflict handling explicitly: overlapping windows allowed; actual concurrency bounded globally/per-account, incompatible playback exclusive; contention skips/delays only within validity window. Background music may overlap reading another provider if allowed. Account failure is local, not whole scheduler failure. Startup/restart doesn't replay missed public posts or uncertain sends. Scheduled action rechecks permissions/config/account/budget immediately before write.
Public notifications/replies can remain event-driven under shared gates; global planner must not delay an explicit permitted user request unnecessarily. New schedule mutation affects future tasks; define cancellation of running tasks vs already-sent actions. No rollback claim for actions already published.
